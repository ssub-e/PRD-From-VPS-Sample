# Gemini-V1 vs Opus-V1 비교 분석

두 통합 문서는 동일한 원본(`01_value-proposition-draft.md` + `02_job-feature-map+MVP-plan.md`)을 기반으로 하지만, **문서 구조·정보 밀도·확장 전략** 측면에서 뚜렷한 차이를 보입니다.

---

## 1. 구조적 차이 요약

| 비교 항목 | **Gemini-V1** (194줄, 17KB) | **Opus-V1** (93줄, 9KB) |
|---|---|---|
| **버전 표기** | `V1` (헤더 메타 정보에 명시) | `Opus-V1` (제목 바로 아래 배지) |
| **목차** | ✔ 앵커 링크 포함 목차 제공 | ✖ 목차 없음 |
| **VPS ↔ Feature 상호참조** | ✔ 각 페르소나 하단에 `🔗 연관 MVP 기능` 링크 | ✖ 없음 |
| **MVP 상세 계획 구조** | **Feature-by-Feature** (F1~F6 각각 독립 테이블) | **Phase-by-Phase** (Sprint 1→2→3 시간순 로드맵) |
| **Post-MVP 범위** | F4·F5·F6 각각 별도 섹션으로 상세 서술 | 3-3절 테이블 한 장으로 요약 |
| **통합 원본 추적** | 헤더에 원본 파일명 명시 | 푸터 한 줄로 명시 |

---

## 2. 핵심 차이 3가지

### 차이 ① — MVP 상세 계획의 설계 관점

가장 결정적인 차이입니다.

| | Gemini-V1 | Opus-V1 |
|---|---|---|
| **관점** | **기능(Feature) 중심** — 각 Feature를 독립 단위로 분해 | **시간(Phase) 중심** — 3 Sprint 로드맵으로 시간순 배치 |
| **서술 방식** | F1~F6 각각에 대해 페르소나·기술요소·KPI·리스크를 개별 테이블로 정리 | Phase 1(데이터)→Phase 2(모델)→Phase 3(프론트) 순서로 기술 스택·산출물·리스크를 묶어 서술 |
| **기능 간 의존성** | F3→F2 의존성을 리스크/의존성 란에 텍스트로 명시 | Phase 순서 자체가 의존성을 암시 (Phase 1 완료 후 Phase 2 착수) |

### 차이 ② — 정보 밀도와 문서 분량

| | Gemini-V1 | Opus-V1 |
|---|---|---|
| **분량** | ~194줄 / 17KB | ~93줄 / 9KB |
| **Post-MVP** | F4·F5·F6 각각 독립 섹션(기술요소·KPI·진입 조건까지 상세) | 3행짜리 요약 테이블 |
| **KPI** | 기능별로 구체적 수치 KPI 제시 | MVP 스코프 요약 테이블에 3개 통합 KPI만 제시 |

### 차이 ③ — 네비게이션 & 문서 이동성

| | Gemini-V1 | Opus-V1 |
|---|---|---|
| **목차** | 앵커 링크 목차 → 클릭으로 섹션 이동 가능 | 없음 |
| **상호참조** | 페르소나 → 연관 Feature 양방향 링크 | 없음 |

## 3. 장단점 평가

### Gemini-V1

| 장점 | 단점 |
|---|---|
| ✅ **Feature별 독립 상세 테이블** — 개발팀에게 "이 기능만 보면 된다"는 단위 전달이 명확 | ❌ **분량이 2배** — 전체 줄거리 파악에 시간 소요 |
| ✅ **목차 + 앵커 링크** — 194줄 문서를 빠르게 탐색 가능 | ❌ **시간순 실행 흐름이 보이지 않음** — "무엇을 먼저 만들지?"에 대한 직관적 답이 약함 |
| ✅ **페르소나 ↔ Feature 상호참조** — VPS와 Feature Map 사이의 논리적 연결이 가시적 | ❌ **Feature 중복 컨텍스트** — 페르소나 정보가 VPS 테이블과 Feature 테이블에서 반복 |
| ✅ **Post-MVP도 상세 서술** — 장기 로드맵 관점에서 투자자/경영진 커뮤니케이션에 유리 | ❌ **MVP와 Post-MVP 경계가 흐릿** — F4~F6도 동일한 상세도로 서술되어 우선순위 강조가 약해짐 |
| ✅ **기능별 리스크/의존성 명시** — 개발 계획 시 누락 방지 | |

### Opus-V1

| 장점 | 단점 |
|---|---|
| ✅ **Phase(Sprint) 기반 로드맵** — "어떤 순서로 무엇을 만들 것인가"가 한눈에 보임 | ❌ **목차·상호참조 없음** — 문서 내 탐색성 부족 |
| ✅ **간결한 분량(9KB)** — 빠른 전체 읽기와 공유에 유리 | ❌ **기능별 개별 KPI 부재** — F1·F2·F3 각각의 성공 기준이 통합 KPI에 묻힘 |
| ✅ **기술 스택 명시** — Phase별로 구체적 기술(FastAPI, Airflow, PyTorch 등) 제시 | ❌ **Post-MVP 상세도 부족** — F4·F5·F6의 진입 조건·리스크가 생략됨 |
| ✅ **MVP 스코프 요약 테이블** — 기간·대상·KPI가 한 테이블로 압축되어 경영 보고에 적합 | ❌ **기능 간 의존성이 암시적** — Phase 순서에 의존하므로 명시적 추적이 어려움 |
| ✅ **MVP vs Post-MVP 경계가 선명** — MVP 포함 기능만 상세 서술하여 집중도 높음 | |

## 4. 용도별 추천

| 용도 | 추천 문서 | 이유 |
|---|---|---|
| **개발팀 핸드오프** | Gemini-V1 | 기능별 독립 테이블로 개발 단위 분해가 명확하고, 리스크/의존성이 기능 단위로 추적 가능 |
| **경영진/투자자 보고** | Opus-V1 | 간결한 분량 + Sprint 로드맵 + MVP 스코프 요약이 의사결정 커뮤니케이션에 최적 |
| **장기 제품 로드맵** | Gemini-V1 | Post-MVP(F4~F6)까지 상세 서술되어 있어 전체 제품 비전 전달에 유리 |
| **빠른 팀 온보딩** | Opus-V1 | 9KB 분량으로 신규 팀원이 전체 그림을 빠르게 파악 가능 |

## 5. 최적 통합안 제안

두 문서의 장점을 결합하면 다음과 같은 **V2 구조**가 가능합니다:

```
1. VPS (Problem–Solution Fit)         ← 원본 유지
   └ 각 페르소나 하단에 연관 Feature 링크   ← Gemini-V1 장점
2. Job–Feature Map                    ← 원본 유지
3. MVP 구현 상세 계획
   ├ 3-1. MVP 스코프 요약 (테이블)       ← Opus-V1 장점
   ├ 3-2. Phase 로드맵 (Sprint 1→2→3)   ← Opus-V1 장점
   └ 3-3. Feature별 상세 명세 (F1·F2·F3) ← Gemini-V1 장점
4. Post-MVP 확장 로드맵
   └ F4·F5·F6 상세 명세               ← Gemini-V1 장점 (축약 가능)
```

> [!TIP]
> 이 구조는 **"먼저 전체 그림(Phase)을 보고 → 세부 기능(Feature)으로 드릴다운"** 하는 Top-Down 읽기 흐름을 제공합니다.
